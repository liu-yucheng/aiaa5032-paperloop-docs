Release notes

Changelog

This page records the user-visible change of each version. Release dates follow the Git tags. The 0.14.1 entry is the current release. The plugin version is also in src/constants.ts and package.json.

0.14.1

21 November 2026

This release allows more than one figure in a report, moves the score weights of the Evaluator into the parameters, limits one weight change to a fixed step, and states every time limit in seconds as a float. The plugin now enforces 1080 seconds on each forward, validation, and test pass and 180 seconds on each backward pass.

One or more figures in a report

  • A report carries one or more PNG images. Each image stays at or below 3840 by 2160 pixels.
  • The media index gives every image one title, and the report names each file and each title.
  • The report prompts, the validation requirements, the audit detail, and the help page state the new rule.

Score weights in the parameters

  • The field weights of configs_rw/v<N>/evaluator/config.json holds one weight for each of the five quality aspects and the weight weakest.
  • The score of one task is (1 - weakest) * sum(weight * aspect) + weakest * min(aspect). The five aspect weights sum to 1, and weakest stays from 0 to 0.5.
  • configs_ro/v<N>/rsi.json holds evaluation.maxWeightStep, which is 0.05 by default. The Evolver changes one weight by at most that step in one version, and the plugin rejects a larger change.
  • The loss uses the weights of the active parameters version, so a gradient can lower the loss by moving a weight that the evidence supports.

Seconds as one unit and one float type

  • Every stage time limit, scale limit, and exploration budget is a number of seconds. A stored time length is a float with millisecond precision.
  • The attempt durations are durationSeconds instead of durationMilliseconds.

Enforced pass wall clock

  • The plugin enforces 1080 seconds on each forward, validation, and test pass, and 180 seconds on each backward pass.
  • paperloop.json no longer holds maxRunMinutes, because the pass wall clock is a policy, not a parameter.

Verification

  • npm run typecheck, npm test, and npm run smoke pass.

0.14.0

21 November 2026

This release removes the video requirement, scores the deliverable quality on five aspects, shows the validation rules in every stage prompt, and replaces a meaningless rerun with one repair pass. Each stage now has a soft time limit and a hard time limit.

Report media

  • A report carries at least one PNG image at or below 3840 by 2160 pixels. One figure is enough.
  • The plugin asks for no video and checks for no video. Video rendering took longer than the stage time limit allowed, so it caused failed validations without a reason.
  • The media index, the media title, the front page flag, and the report reference rules stay unchanged.

Loss over five quality aspects

  • Each task record carries five aspect scores from 0 to 5: completion, correctness, depth, presentation, and reproducibility. The evaluation record has schema version 3.
  • The score of one task is 0.6 * mean(aspects) + 0.4 * min(aspects). The weakest aspect weighs 40 percent of the score, so one weak aspect is not hidden by four strong aspects and the loss separates two different products.
  • The overall qualityScore must stay within 1.0 of the aspect mean. The audit metrics and the help page state the new formula.

Validation rules in the prompt, and one repair pass

  • Every stage prompt holds a section that lists the rules that the validator checks, with the identifier of each rule. A subagent reads the same rules that the validator applies.
  • When a rule fails and the subagent returned OK, the plugin sends one repair message into the same subagent session. The message names the missing rules and asks for the missing items only, so the earlier work stays.
  • A repair pass is not a retry. The plugin counts a retry only for a RETRY result, an agent error, or a hard time limit.

Soft time limit and hard time limit

  • The time limit in the prompt is the soft limit. The hard limit is twice the soft limit.
  • A stage may run past the soft limit. When it completes the task, the plugin keeps the result and records one time limit event, which the self-evaluation counts in the human intervention burden.
  • The plugin stops a stage at the hard limit and starts one fresh attempt. That attempt counts as a retry. The audit reports soft_limit_overruns and hard_limit_stops.

Verification

  • The test suite covers the two time limits, the requirement table, the rules section of a stage prompt, the repair message, the five aspect scores, and the aspect consistency rule.

0.13.0

21 November 2026

This release shortens the wall clock of every pass, keeps every experiment at the minimal scale, adds a manual resume for a stopped stage, and makes the PaperLoop tab scroll with the mouse wheel.

Pass wall clock

  • A forward, validation, or test pass stops at 18 minutes. The plugin checks the deadline before each retry, so a retry chain cannot exceed it.
  • A backward pass stops at 3 minutes. The stage limits of the eight stages are now 120, 180, 90, 75, 150, 75, 90, and 60 seconds, and the shared exploration budget is 240 seconds.
  • Every subagent runs experiment code at --minimal-scale only. The plugin rejects a run manifest that records the reduced scale or the full scale. The two other flags stay in the entry script for a human reader.

Manual resume

  • Every stage record keeps the subagent session identifier, the provider, the cause of the last stop, and the number of resumes.
  • /paperloop_resume [<index|session_id>] [--stage <id>] continues the session at the stage where it stopped. The pass keeps every stage that already has an ok status, and the prompt of the resumed stage names the earlier subagent session.
  • A manual interrupt stops the stage as cancelled, and a network failure stops it as a network stop. Neither one records a human intervention. An agent failure, a program failure, and a time limit still record one.

PaperLoop tab

  • The tab root now declares data-conversation-composer-overlay and owns the vertical scroll. The host gives the view column a definite height, so the mouse wheel scrolls the page instead of a hidden parent box. Dragging the scrollbar is no longer the only way to move the page.

0.12.1

18 November 2026

This release makes the workspace hygiene rule a requirement that the plugin checks. Before this release the prompt gave the rule to every subagent, and no stage and no audit measured it.

Workspace hygiene

  • The temporary-file rule now names each cache directory that a runtime creates without a dot: __pycache__/, node_modules/, target/, .pytest_cache/, .mypy_cache/, .ruff_cache/, and .ipynb_checkpoints/. It also names each scratch file pattern: *.pyc, *.pyo, *.tmp, .DS_Store, Thumbs.db, and Rplots.pdf.
  • The rule states that a later run prepares the environment again with uv sync or uv run, because the cleanup deletes every .venv/ directory.
  • A new module src/hygiene.ts scans the original code tree, the three code task trees, and the two report trees. A dot directory is temporary unless it is an ignored name such as .git/, .github/, or .vscode/. The scan reports at most 20 leftover paths.
  • The stage gate calls the scan after each stage. A leftover path adds one missing artifact to the stage result, so the stage returns RETRY and the message names the paths.
  • The audit gains the check workspace_hygiene. Its detail names every leftover path, or states that no temporary path remains.

0.12.0

18 November 2026

This release changes the rollback policy of the validation pass. The plugin now rolls the parameters back when the validation loss grows worse for several passes in a row, and not when one pass is worse than the best loss. The number of passes is a setting of the plugin page.

Validation rollback

  • A pass is worse when its mean loss is worse than the mean loss of the pass before it by more than the tolerance. A pass that improves or holds the loss sets the worse streak to zero.
  • The plugin copies the best version to a new version number when the worse streak reaches the rollback threshold. The default threshold is three consecutive worse passes. A rollback sets the streak to zero, so the next rollback needs a new streak of worse passes.
  • The threshold accepts a whole number from 1 through 10. The field validationRollbackStreak on the plugin settings page sets it, and a field value of 0 uses the value in paperloop.json. The read-only default is validation.rollbackStreak, which is 3.
  • The record in evals/validated/decisions.json gains the fields worseStreak and streakLimit. The settings page shows the default threshold and the effective threshold.
  • The settings bridge gains the route /paperloop/settings/rollback, and the settings page gains the panel "Validation rollback".

0.11.0

16 November 2026

This release adds the exploration loop, the code layout of the training prompt, and the runtime product. A forward pass now runs seven stages: runtime setup, reproduction code, reproduction report with up to three exploration rounds, innovation code, innovation report, and self-evaluation. Self-evolution stays in the backward pass as stage 8.

Stages and exploration

  • One stage joins the forward pass: exploration_code. The Researcher writes the exploration analysis as the last part of reproduction_report, so a round runs the Coder and then the Researcher again.
  • The Researcher asks for code by writing one instruction file in exploration/instructions/, named round_<n>.md, and delegates the work to the Coder. The Researcher writes no code.
  • The reproduction report writes exploration/directions/decision.json with exploreMore, selectedDirection, and reason. The plugin stops the loop at the round limit maxExplorationRounds, at the budget explorationBudgetSeconds, at the session deadline, or when a decision asks for no round.
  • The eight stage time limits are 300, 300, 240, 120, 200, 180, 120, and 90 seconds. They add up to 25 minutes and 50 seconds, and the exploration rounds use a budget of 12 minutes.

Runtime

  • The product of the Runtime stage is the debugged original code with pyproject.toml and main.py. The subagent keeps the modification of the original code as small as possible.
  • main.py accepts --minimal-scale, --reduced-scale, and --full-scale. The Runtime subagent runs the minimal scale once and finishes within 30 seconds. It never runs another scale.
  • minimal_run.json records the scale, the command, the seconds, the exit code, the device, the device support, and the uv command.

Coder

  • Every code stage writes one layout: {source,docs,inputs,outputs}. The output directory is a normal directory, so a later stage reads it read-only.
  • The Coder copies the components of an earlier stage and never modifies an earlier codebase. The plugin stores a fingerprint of the reproduction code and reports a change.
  • The reproduction and the innovation task run the code twice: the minimal scale, then the reduced scale when the minimal run passed, and the minimal scale again when it did not. The exploration task runs the minimal scale once.
  • The reduced scale must finish within 120 seconds. The full scale is a reference to the paper scale, not a strict limit, and no subagent runs it.
  • The Runtime and the Coder manage Python and every dependency with uv. Each code stage supports a CPU-only device and a CPU with a GPU, and the manifest records both.

Reports

  • The reproduction report is concise and critical, is about the computational results of the paper, names its limitations and its future work, and ends with the one selected exploration direction.
  • The report cites a result of the paper instead of claiming that the minimal run reproduced it.
  • Each report carries at least one PNG image of at most 3840 by 2160 pixels and at least one MP4 video of at most 30 seconds at 1920 by 1080 pixels.
  • Each media file has one entry in media/media.json with a title and a frontpage flag. One entry is the frontpage, and the report body contains the title and the file name of every media file.
  • The innovation report clearly distinguishes the explored direction from the directions of the original paper.
  • Every file under the paper workspace uses the non-strict mode of ASD-STE100 with academic US English fallback. The optional --language <language_and_style_specification> argument of /paperloop_forward, /paperloop_validate, and /paperloop_test replaces that default for one pass. Every file under the app data keeps the default without exception.

Budget and help

  • The stage limits of stages 1 to 7 add up to 1140 seconds and the exploration rounds draw from a shared budget of 480 seconds, so a complete forward pass stays inside the 30-minute budget.
  • A validation pass and a test pass keep a wall clock of 24 minutes, because neither writes a gradient.
  • The plugin settings page sets the time limit of each stage, shows the four budgets, and warns when the stage limits and the exploration budget exceed the forward budget.
  • /paperloop_help prints one compact page. The optional --topics <topics> argument asks a subagent for a detailed page, which the plugin caches in <app-data>/help/.

Evaluation

  • The Evaluator scores the five tasks, not the five forward stages. evals.json has schema version 2 and holds tasks, totals, and metrics.
  • A task entry has the product, a quality score from 0 to 5, one critical evaluation, the human hours, the reason for the estimate, and the evidence.
  • The plugin writes no rubric file. The loss is the mean of 1 - qualityScore / 5 over the five tasks.
  • The scorecard reports task completion rate, human intervention burden, delegation completion cost, output parity, report compile rate, and media validity rate. The rubric agreement metric is removed.

0.10.0

16 November 2026

This release makes the human interface usable in an ordinary chat session. A PaperLoop line now runs from the composer, shows its result in the transcript, names its session, and feeds one PaperLoop view. The seven stages, the five subagents, the stage time limits, and the read-only configuration policy are unchanged.

Chat interface

  • The plugin registers its own / input source for the eight PaperLoop names. A PaperLoop line therefore runs in every chat session, including a new empty session, and it does not depend on the Harness command catalogue.
  • The plugin removes one leading @ from each argument. A line that names @D:\papers\attention.pdf now opens that file, and it no longer reports The paper file does not exist.
  • /paperloop, /paperloop_forward, /paperloop_validate, and /paperloop_test accept a paper PDF that the user attaches to the command. The other commands refuse an attachment with one sentence and keep the draft.
  • A PaperLoop line that arrives as ordinary chat text runs through the matching tool. The system prompt states this route, so the model does not ask the user to retype the command.
  • The help manual gains the topic chat. It describes the two input styles and the two ways to give a paper.

Command results

  • A PaperLoop command shows one command row in the transcript. The row carries the state, the elapsed time, the loss, one row for each session with the session identifier and the workspace path, and the app data path.
  • The first PaperLoop command of a session that has no turn starts the first turn. The command row, the context line, and the sidebar entry therefore appear at once, and the session becomes persistent.
  • A command in a session that already has a turn appends one notice of at most 120 characters. The transcript keeps the full output in the command row.
  • A failed command reports one line in the composer. A successful command stays silent in the composer, because the transcript row carries the result.

Session identity

  • The first PaperLoop command of a session writes the title PaperLoop: <command> <paper stem> once. Later commands keep the title.
  • The plugin writes the title through the sessionTitle service. When that service is absent, the plugin appends the session/title event itself.

PaperLoop view

  • The plugin adds one PaperLoop tab next to Chat, Trajectory, and Git Graph. The tab shows the parameters version, the loss of each split as a sparkline, the checkpoint table, the rubric heatmap, and the sessions with the artifact paths.
  • The tab fills the conversation column and scrolls vertically. Its horizontal padding matches the toolbar above it.
  • The panel is read-only. It names each file, and one button copies a path to the clipboard, because a browser does not open a file: address from the Harness page.

Parameters state route

  • The read-only route GET /api/dsh-aiaa5032-paperloop-settings/state returns the projection that feeds the view, the command row, and the progress strip.
  • The projection reports only what the files on disk support. An absent loss is null, and the route never reports an unverified result.

Tools

  • The plugin adds the tools paperloop_help and paperloop_clear_appdata. The plugin now registers ten tools and eight commands.
  • paperloop_clear_appdata changes nothing unless the call sets confirm to true. Without the confirmation it returns the inventory of a reset.

Fixes

  • paperloop_status no longer fails with value is not lossless JSON. The tool output no longer carries a property with the value undefined.
  • The plugin writes a surface notice only when the session already holds the protected first surface head. A notice written before that head made the stored session corrupt, and the history failed to load.
  • The composer result panel is removed. The command row and the PaperLoop view replace it.

0.9.2

15 November 2026

This release keeps the workspace root clean. One pass writes one paper sub-workspace and no other plugin directory. The seven stages, the five subagents, the eight tools, the stage time limits, and the read-only policy are unchanged.

Workspace root

  • One paper pass writes one directory <workspace>/<timestamp>_<paper_stem>_<rerun_count>/ in the workspace root, also when the pass names one paper.

0.9.1

15 November 2026

This release makes the workspace of one paper unique for every pass. A repeated pass on the same paper now writes a separate sub-workspace and a separate session. The seven stages, the five subagents, the eight tools, the stage time limits, and the read-only policy are unchanged.

Paper workspace and session identifier

  • Each paper pass uses the sub-workspace <workspace>/<timestamp>_<paper_stem>_<rerun_count>/.
  • The same string is the session identifier in sessions/, evals/<split>/, and evolutions/pending/. One string names one pass.
  • The rerun count starts at 0 and counts the earlier passes on the same paper in the same workspace. A repeated pass never reuses the workspace or the session of an earlier pass.
  • The paper stem keeps its letters. Only a character that a directory name rejects becomes a hyphen. The former -2 and -3 suffix is gone.

Session selectors

  • /paperloop_backward and /paperloop_feedback accept a 1-based session index or a session identifier. The index is the position of the session in creation order.
  • The pending list prints the index in front of the identifier, so a user can copy the index into the next command.
  • A selector that names no plan or more than one plan prints one message and changes nothing.

0.9.0

15 November 2026

This release widens the Coder from Python to nine languages and makes the refactored code a reusable library with a generated documentation website. The seven stages, the five subagents, the eight tools, the stage time limits, and the read-only policy are unchanged.

Language scope

  • The Coder writes Python, C, C++, R, MATLAB, Fortran, TypeScript, JavaScript, and SQL. The set covers more than 93 percent of the academic papers that publish a code repository.
  • The Coder keeps the language of the original repository. It changes the language only when the original code cannot run in this environment, and it states the reason in run_manifest.json.
  • The scale rules are language-neutral. The main entry script of the refactored code accepts the three scale flags. When the language cannot read a flag, main.py is a thin launcher that passes the scale to the language entry point.
  • The Runtime subagent creates the environment with uv for a Python project and with the native package manager of another language.

Reusable library

  • The Coder treats each reusable part as a Plug and Play library at code/source/<package_name>/. One module has one responsibility and one public function or class for one task.
  • A public function takes its input as a parameter and stays pure when the task allows it. The code has no global mutable state, no hard-coded absolute path, and no side effect at import.
  • One module index file exports the public names: __init__.py for Python, index.ts for TypeScript, index.js for JavaScript, NAMESPACE for R, and +<package_name>/ for MATLAB.
  • One dependency manifest declares the library dependencies: pyproject.toml, package.json, DESCRIPTION, Project.toml, fpm.toml, or a Makefile. The tests are under source/tests/ and one usage example is under source/examples/.
  • The entry script calls the library. It does not repeat the same logic.

Documentation website

  • The Coder generates a documentation website for the library. A reproduction task writes to reproduction/code/docs/index.html. An innovation task writes to innovation/code/docs/index.html.
  • A documentation generator writes the pages: pdoc or MkDocs with mkdocstrings for Python, Doxygen for C, C++, MATLAB, and Fortran, ford for a Fortran project with FORD comments, pkgdown for R, TypeDoc for TypeScript, JSDoc for JavaScript, and SchemaSpy or tbls for SQL.
  • The Coder hand-writes a page only when the generator is absent or it fails on the project. It then states the reason in run_manifest.json.
  • The Coder checks that docs/index.html exists and that the website lists each public module.
  • run_manifest.json gains the fields language, library, and documentation. The last field holds the generator name, the generator command, and the entry path.

Artifact gate and audit

  • The Coder artifact gate accepts any source file with a supported extension instead of a .py file. It also requires docs/index.html in the documentation directory.
  • The session layout gains reproductionDocs and innovationDocs. The service creates both directories with the other batch directories.
  • The audit adds the checks reproduction_docs and innovation_docs. A check passes when the website has an index.html entry. No metric and no rsi.json field changes.
  • The Coder stage prompt and the Coder configuration Markdown name the supported languages, the library rules, and the documentation rules. The paths section and the required artifacts section of each Coder stage name the library and the documentation website.

0.8.0

15 November 2026

This release adds the help manual and the factory reset. A new user can ask the plugin how to start, and an experienced user can return the app data to a clean state. The release also replaces the three style guides with the current two guides: natural language, and code styles for every language. The seven stages, the five subagents, the eight tools, and the read-only policy are unchanged.

The help manual

  • /paperloop_help [<question> ... | <topic_id>] prints one answer. With no argument it prints the topic list and the live state of this machine.
  • The manual has twelve topics: start, forward, backward, validate, test, feedback, inspect, appdata, reset, scale, metrics, and troubleshoot.
  • A keyword score selects the topic. An ASCII keyword matches a whole word and a Chinese keyword matches a substring. A question that matches no topic prints the topic list with a short note, so the user always receives a way forward.
  • Each answer ends with a Now block: the app-data path, the parameters version, the session count, the pending gradient count, the effective stage time limits, the last session, and the next command.
  • The manual makes no model call. It is deterministic, so a test asserts the text of each branch.

Factory reset

  • /paperloop_clear_appdata [--yes] deletes the app data and copies the packaged default_app_data seed back into it.
  • Without --yes the command prints a preview: the path, the session count, the evaluation records, the pending and applied gradients, and the parameter versions. It changes no file.
  • An unknown option is an error that prints the usage line.
  • The reset deletes sessions/, evals/, evolutions/, history/, and configs_rw/. It restores configs_ro/v0/ and configs_rw/v0/CHECKPOINT.json. Papers and sub-workspaces stay in place.
  • The reset rejects a path that is the packaged seed or a child of it. The plugin settings page keeps its own reset route.

Main command

  • /paperloop help [<question>], /paperloop h, and /paperloop ? call the help manual.
  • /paperloop clear and /paperloop reset call the factory reset.
  • The plugin now has eight commands and eight tools. Help and factory reset are commands only, because a tool call cannot show a preview and wait for a confirmation.

Style guides

  • Two guides replace the three earlier guides: natural_language_styles and code_styles. The code guide covers the general rules, Python, C, C++, R, MATLAB, Fortran, TypeScript, JavaScript, SQL, and the fallback.
  • The general rules put readability first. They require a documentation string for each function, type, module, and constant, set the line length to 119 characters, and define the reproduction baseline: inputs/ read-only, .outputs/ read-write, the tool versions, and the random seed.
  • The stage prompt section "Python and execution" is now "Code style and execution". It carries the general rules, the Python rules, and the scale rules. The configuration Markdown carries the same rules.
  • The Chinese rule appears in the stage prompt and the system prompt: Simplified Technical Chinese non-strict mode.
  • The documentation site has two style pages, natural_language_styles.html and code_styles.html. The two older pages are removed. AGENTS.md, CLAUDE.md, and the API front page name the two current guides.

Documentation

  • The app-data README.md lists the help command and the factory reset.
  • The README command list names paperloop_status, paperloop_audit, and paperloop_config as tools. The earlier list showed /paperloop_status as a command.

0.7.0

14 November 2026

This release turns the plugin into a training loop. The user trains, validates, and tests the PaperLoop agentic system as one trains a neural network. The release also adds the feedback pass, which lets a human correction enter the loss and the gradient before the backward pass, and two diagrams that show the loop and the stage roles. The seven stages, the five subagents, and the read-only policy are unchanged.

The training-loop mapping

  • The parameters are the files in configs_rw/v<N>/. One version is one point in the parameter space.
  • The data items are the paper PDF files. A split selects the purpose of a pass: training, validation, or test.
  • The loss function is the evaluator. The plugin reduces the five stage scores to one scalar loss: loss = mean(1 - score / 5). An unscored stage counts as 1.0.
  • The gradient is the evolution plan. The backward pass applies it and writes the next parameters version.
  • A checkpoint is configs_rw/v<N>/CHECKPOINT.json. It records the parent version and the training loss and the validation loss of that version.

New commands and tools

  • /paperloop_validate and the tool paperloop_validate run the validation split. The pass writes a loss to evals/validated/ and one decision to evals/validated/decisions.json. A loss that is worse than the best validation loss by more than the tolerance copies the best version to a new version number.
  • /paperloop_test and the tool paperloop_test run the test split. The pass writes a loss to evals/tested/ and one report to evals/tested/reports.json. It changes no parameter.
  • Each pass writes one loss.json in its evaluation directory. A subagent does not write that file.
  • /paperloop_status reports the parameters version, the best validation loss, and the latest loss of each split.
  • /paperloop_feedback and the tool paperloop_feedback accept pairs of --session=<id> and --feedback=<text>. Each pair names one pending session.
  • The plugin now has eight tools and six commands. The stage catalog still has seven stages.

Human feedback

  • The plugin appends one record to evals/pending/<session>/feedback.json. The identifier is fb001, fb002, and so on.
  • The plugin runs stage 6 again with the feedback text in the prompt. The Evaluator lowers a score only when the evidence supports the feedback. It writes one entry in the feedback array of gradient.json for each record.
  • The stage fails when one feedback identifier has no entry in the gradient. A lost signal is not a valid pass.
  • The plugin recomputes loss.json and rewrites evolutions/pending/<session>/plan.json. The pass writes no parameters version and moves no applied record.

Documentation

  • The contract page has two figures. Figure 1 shows one epoch of the loop. Figure 2 shows the subagent of each stage.
  • The contract page describes the feedback pass and the feedback array of gradient.json.
  • The plugin icon and the documentation site share one mark. The mark is a page, and the loop arrow is inside the page.
  • The web pages use free fonts only. Noto Sans is the sans-serif font, Noto Serif is the serif font, and Cascadia Mono is the monospace font. All three fonts carry the SIL Open Font License. No commercial font is named in the stylesheet, the figures, or the icon. The wordmark of the logo is a vector outline made from Noto Sans Bold, so the logo renders the same without an installed font.

Behaviour changes

  • A session identifier no longer starts with an underscore. The form is <YYYYMMDDTHHMMSS>_<short_topic>.
  • One /paperloop_forward accepts several paper files. Each paper writes its own session under evals/pending/ and evolutions/pending/. One /paperloop_backward accepts several session identifiers.
  • A feedback request without a pending evaluation record is an error. The message names the training pass that the user must run first.
  • A feedback request without a session option or without a feedback option is an error. The plugin changes nothing.
  • A validation pass and a test pass create no evolution directory. Only a training pass writes a gradient.
  • The packaged seed contains configs_rw/v0/CHECKPOINT.json. Run npm run seed to regenerate the seed.

0.6.0

13 November 2026

This release makes the self-evaluation evidence-checked. A score needs a recorded reason and an existing evidence file. The seven-stage architecture is unchanged.

Evaluation record

  • The Evaluator scores the five forward stages. It writes one pair for each stage and does not score self_eval or self_evolve.
  • A pair has agent, stage, rubricId, criterion, verdict, score, reason, uncertainty, and evidence.
  • A supported verdict scores 5. A contradicted verdict scores 1. An insufficient verdict has a null score and the uncertainty flag.
  • Each evidence reference names an existing file in the paper workspace or the app data. A reference can add a line and a pointer.
  • evals.json has schema version 1, the session ID, a one-sentence scope, pairs, weakStages, unassessedStages, and tokenCostEfficiency.
  • rubrics.json is append-only. Every earlier entry stays unchanged. A new entry needs a new identifier.
  • The plugin recomputes the token cost efficiency from the recorded attempts. The status is available, partial, unavailable, or zero_denominator.
  • The plugin checks that evals.md names each stage and rubric ID and shows each numeric score as N/5. A mismatch fails the stage attempt.

Audit and prompts

  • Rubric agreement now counts the five forward pairs that have a rubric record. The earlier metric used six pairs.
  • The Evaluator configuration and prompt state the record fields and the fixed scores. The self-evaluation guidance names the applied evaluation directory.

Compatibility and documentation

  • The plugin version is 0.6.0. The configuration schema version and the state schema version stay at 2.

0.5.0

13 November 2026

This release cuts a full forward pass to 30 minutes. It also replaces the setup/run interface with a forward pass and a backward pass.

Human interface

  • The plugin now uses the current DeepSeek Harness session workspace as the PaperLoop workspace. The separate workspace setting and the paperloop_setup tool are removed.
  • /paperloop is the main command. It takes the forward or backward action.
  • /paperloop_forward asks for one or more paper PDF files. Each valid paper runs stages 1 to 6 in its own sub-workspace <workspace>/<paper_stem>/.
  • /paperloop_backward lists the sessions with a pending evolution plan. The user selects one or more sessions. Only this action updates configs_rw/.
  • An empty selection exits with no file change. The plugin returns the question as command text, because a command cannot prompt interactively.
  • The tools are now paperloop_forward, paperloop_backward, paperloop_status, paperloop_audit, and paperloop_config.

Time and scale

  • The seven stage limits are 300, 300, 300, 240, 240, 180, and 120 seconds. The sum is 28 minutes.
  • Runtime and Coder no longer run a full-scale or a reduced-scale experiment. They run one minimal setup that must finish in 30 seconds or less.
  • A main script accepts one scale flag: --minimal-scale (default, 30 seconds or less), --reduced-scale (5 minutes or less), or --full-scale (no limit). A human user runs the last two flags after the session ends.
  • Runtime and Coder do not produce or reproduce a computational result. A minimal run proves that the code runs without a bug.
  • rsi.json replaces codeTimeLimitSeconds with minimalScaleSeconds, reducedScaleSeconds, and fullScaleSeconds.

Stages

  • The stage identifiers are now runtime_setup, reproduction_code, reproduction_report, innovation_code, innovation_report, self_eval, and self_evolve.
  • The Researcher writes the innovation direction into reproduction/report/report.typ and report.pdf. The direction comes from the limitations and the future work in the original paper.
  • The Coder reads the Innovation direction section of that report. The innovation manifest records the direction and the hypothesis.

Evaluation and evolution

  • A successful forward pass writes the self-evaluation to <app-data>/evals/pending/<session>/ and the evolution plan to <app-data>/evolutions/pending/<session>/.
  • The Evaluator writes gradient.json next to evals.json, evals.md, and rubrics.json. The plugin copies the gradient to plan.json in the evolution directory.
  • A successful backward pass writes configs_rw/v(K+1)/ with five configuration files, five prompts, and EVOLUTION.md. It then moves the plan and the evaluation to their applied/ directories.
  • The Evolver cannot change a stage time limit, a scale limit, an evaluation target, an integrity rule, or an existing rubric entry.
  • The audit writes scores.json and scores.md into the session evaluation directory. Output parity is 100 percent by default, because a minimal run claims no computational result.

Compatibility and documentation

  • The configuration schema version and the state schema version are now 2. The plugin version is 0.5.0.
  • The settings page shows the seven renamed stage limits and the new app-data fields. The copy now names a session instead of a run.
  • This changelog page is new. The subagent contract page describes the forward pass, the backward pass, and the pending and applied directories.
  • The TypeScript style guide now matches the Python style guide. The maximum line length is 119 characters. A line break follows a complete doc comment sentence. A hanging indent aligns horizontally.

0.3.0

7 November 2026

This release improves the subagent prompts and adds token cost accounting.

  • The Evaluator reports token cost efficiency (TCE). TCE is the number of completed agent-task pairs per one million billed tokens.
  • The plugin captures token usage from each child session. The usage covers input, output, cache read, and cache write tokens.
  • A new temporary-file rule keeps scratch files in a dot directory. The rule requires cleanup of every temporary file, temporary directory, and .venv directory before a stage returns.
  • The stage prompts, subagent configuration files, app-data README, contract page, and packaged seed carry the new rules.

0.2.0

6 November 2026

This is the first implementation of the PaperLoop plugin. It replaces the template placeholder with the stage workflow.

  • The plugin ran seven stages for one paper: runtime, reprod_code, reprod_report, innov_code, innov_report, self_eval, and self_evolve.
  • Five subagents ran the stages in isolated child sessions: runtime, coder, researcher, evaluator, and evolver.
  • The tools were paperloop_setup, paperloop_run, paperloop_status, paperloop_audit, and paperloop_config.
  • paperloop_setup created the app-data tree and the reproduction workspace. paperloop_run ran a stage or a slice of stages.
  • The stage time limits were 600 seconds for the first five stages and 300 seconds for the last two stages. Each limit had a plugin setting.
  • The app data held read-only configuration configs_ro/v<N>/, versioned write configuration configs_rw/v<N>/, evaluations evals/v<N>/, stage history, and run state.
  • The audit computed TCR, HIB, DCC, report compile rate, media validity, and output parity. It wrote evals/v<N>/scores.json and scores.md.
  • The plugin included a settings page, a packaged default app data seed, a TypeDoc site, the subagent contract page, and a smoke test.
