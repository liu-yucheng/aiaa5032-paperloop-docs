Release notes

Changelog

This page records the user-visible change of each version. Release dates follow the Git tags. The 0.7.0 entry is the current release. The plugin version is also in src/constants.ts and package.json.

0.7.0

14 November 2026

This release turns the plugin into a training loop. The user trains, validates, and tests the PaperLoop agentic system as one trains a neural network. The release also adds the feedback pass, which lets a human correction enter the loss and the gradient before the backward pass, and two diagrams that show the loop and the stage roles. The seven stages, the five subagents, and the read-only policy are unchanged.

The training-loop mapping

  • The parameters are the files in configs_rw/v<N>/. One version is one point in the parameter space.
  • The data items are the paper PDF files. A split selects the purpose of a pass: training, validation, or test.
  • The loss function is the evaluator. The plugin reduces the five stage scores to one scalar loss: loss = mean(1 - score / 5). An unscored stage counts as 1.0.
  • The gradient is the evolution plan. The backward pass applies it and writes the next parameters version.
  • A checkpoint is configs_rw/v<N>/CHECKPOINT.json. It records the parent version and the training loss and the validation loss of that version.

New commands and tools

  • /paperloop_validate and the tool paperloop_validate run the validation split. The pass writes a loss to evals/validated/ and one decision to evals/validated/decisions.json. A loss that is worse than the best validation loss by more than the tolerance copies the best version to a new version number.
  • /paperloop_test and the tool paperloop_test run the test split. The pass writes a loss to evals/tested/ and one report to evals/tested/reports.json. It changes no parameter.
  • Each pass writes one loss.json in its evaluation directory. A subagent does not write that file.
  • /paperloop_status reports the parameters version, the best validation loss, and the latest loss of each split.
  • /paperloop_feedback and the tool paperloop_feedback accept pairs of --session=<id> and --feedback=<text>. Each pair names one pending session.
  • The plugin now has eight tools and six commands. The stage catalog still has seven stages.

Human feedback

  • The plugin appends one record to evals/pending/<session>/feedback.json. The identifier is fb001, fb002, and so on.
  • The plugin runs stage 6 again with the feedback text in the prompt. The Evaluator lowers a score only when the evidence supports the feedback. It writes one entry in the feedback array of gradient.json for each record.
  • The stage fails when one feedback identifier has no entry in the gradient. A lost signal is not a valid pass.
  • The plugin recomputes loss.json and rewrites evolutions/pending/<session>/plan.json. The pass writes no parameters version and moves no applied record.

Documentation

  • The contract page has two figures. Figure 1 shows one epoch of the loop. Figure 2 shows the subagent of each stage.
  • The contract page describes the feedback pass and the feedback array of gradient.json.
  • The plugin icon and the documentation site share one mark. The mark is a page, and the loop arrow is inside the page.
  • The web pages use free fonts only. Noto Sans is the sans-serif font, Noto Serif is the serif font, and Cascadia Mono is the monospace font. All three fonts carry the SIL Open Font License. No commercial font is named in the stylesheet, the figures, or the icon. The wordmark of the logo is a vector outline made from Noto Sans Bold, so the logo renders the same without an installed font.

Behaviour changes

  • A session identifier no longer starts with an underscore. The form is <YYYYMMDDTHHMMSS>_<short_topic>.
  • One /paperloop_forward accepts several paper files. Each paper writes its own session under evals/pending/ and evolutions/pending/. One /paperloop_backward accepts several session identifiers.
  • A feedback request without a pending evaluation record is an error. The message names the training pass that the user must run first.
  • A feedback request without a session option or without a feedback option is an error. The plugin changes nothing.
  • A validation pass and a test pass create no evolution directory. Only a training pass writes a gradient.
  • The packaged seed contains configs_rw/v0/CHECKPOINT.json. Run npm run seed to regenerate the seed.

0.6.0

13 November 2026

This release makes the self-evaluation evidence-checked. A score needs a recorded reason and an existing evidence file. The seven-stage architecture is unchanged.

Evaluation record

  • The Evaluator scores the five forward stages. It writes one pair for each stage and does not score self_eval or self_evolve.
  • A pair has agent, stage, rubricId, criterion, verdict, score, reason, uncertainty, and evidence.
  • A supported verdict scores 5. A contradicted verdict scores 1. An insufficient verdict has a null score and the uncertainty flag.
  • Each evidence reference names an existing file in the paper workspace or the app data. A reference can add a line and a pointer.
  • evals.json has schema version 1, the session ID, a one-sentence scope, pairs, weakStages, unassessedStages, and tokenCostEfficiency.
  • rubrics.json is append-only. Every earlier entry stays unchanged. A new entry needs a new identifier.
  • The plugin recomputes the token cost efficiency from the recorded attempts. The status is available, partial, unavailable, or zero_denominator.
  • The plugin checks that evals.md names each stage and rubric ID and shows each numeric score as N/5. A mismatch fails the stage attempt.

Audit and prompts

  • Rubric agreement now counts the five forward pairs that have a rubric record. The earlier metric used six pairs.
  • The Evaluator configuration and prompt state the record fields and the fixed scores. The self-evaluation guidance names the applied evaluation directory.

Compatibility and documentation

  • The plugin version is 0.6.0. The configuration schema version and the state schema version stay at 2.
  • The plugin still has seven stages, five tools, and five subagents.
  • A 0.5.0 evaluation record can lack the new fields. The new check rejects such a record. Finish an in-flight session with 0.5.0, or rerun its self-evaluation with 0.6.0.
  • The subagent contract page and the API reference describe the evaluation record.

0.5.0

13 November 2026

This release cuts a full forward pass to 30 minutes. It also replaces the setup/run interface with a forward pass and a backward pass.

Human interface

  • The plugin now uses the current DeepSeek Harness session workspace as the PaperLoop workspace. The separate workspace setting and the paperloop_setup tool are removed.
  • /paperloop is the main command. It takes the forward or backward action.
  • /paperloop_forward asks for one or more paper PDF files. Each valid paper runs stages 1 to 6 in its own sub-workspace <workspace>/<paper_stem>/.
  • /paperloop_backward lists the sessions with a pending evolution plan. The user selects one or more sessions. Only this action updates configs_rw/.
  • An empty selection exits with no file change. The plugin returns the question as command text, because a command cannot prompt interactively.
  • The tools are now paperloop_forward, paperloop_backward, paperloop_status, paperloop_audit, and paperloop_config.

Time and scale

  • The seven stage limits are 300, 300, 300, 240, 240, 180, and 120 seconds. The sum is 28 minutes.
  • Runtime and Coder no longer run a full-scale or a reduced-scale experiment. They run one minimal setup that must finish in 30 seconds or less.
  • A main script accepts one scale flag: --minimal-scale (default, 30 seconds or less), --reduced-scale (5 minutes or less), or --full-scale (no limit). A human user runs the last two flags after the session ends.
  • Runtime and Coder do not produce or reproduce a computational result. A minimal run proves that the code runs without a bug.
  • rsi.json replaces codeTimeLimitSeconds with minimalScaleSeconds, reducedScaleSeconds, and fullScaleSeconds.

Stages

  • The stage identifiers are now runtime_setup, reproduction_code, reproduction_report, innovation_code, innovation_report, self_eval, and self_evolve.
  • The Researcher writes the innovation direction into reproduction/report/report.typ and report.pdf. The direction comes from the limitations and the future work in the original paper.
  • The Coder reads the Innovation direction section of that report. The innovation manifest records the direction and the hypothesis.

Evaluation and evolution

  • A successful forward pass writes the self-evaluation to <app-data>/evals/pending/<session>/ and the evolution plan to <app-data>/evolutions/pending/<session>/.
  • The Evaluator writes gradient.json next to evals.json, evals.md, and rubrics.json. The plugin copies the gradient to plan.json in the evolution directory.
  • A successful backward pass writes configs_rw/v(K+1)/ with five configuration files, five prompts, and EVOLUTION.md. It then moves the plan and the evaluation to their applied/ directories.
  • The Evolver cannot change a stage time limit, a scale limit, an evaluation target, an integrity rule, or an existing rubric entry.
  • The audit writes scores.json and scores.md into the session evaluation directory. Output parity is 100 percent by default, because a minimal run claims no computational result.

Compatibility and documentation

  • The configuration schema version and the state schema version are now 2. The plugin version is 0.5.0.
  • The settings page shows the seven renamed stage limits and the new app-data fields. The copy now names a session instead of a run.
  • This changelog page is new. The subagent contract page describes the forward pass, the backward pass, and the pending and applied directories.
  • The TypeScript style guide now matches the Python style guide. The maximum line length is 119 characters. A line break follows a complete doc comment sentence. A hanging indent aligns horizontally.

0.3.0

7 November 2026

This release improves the subagent prompts and adds token cost accounting.

  • The Evaluator reports token cost efficiency (TCE). TCE is the number of completed agent-task pairs per one million billed tokens.
  • The plugin captures token usage from each child session. The usage covers input, output, cache read, and cache write tokens.
  • A new temporary-file rule keeps scratch files in a dot directory. The rule requires cleanup of every temporary file, temporary directory, and .venv directory before a stage returns.
  • The stage prompts, subagent configuration files, app-data README, contract page, and packaged seed carry the new rules.

0.2.0

6 November 2026

This is the first implementation of the PaperLoop plugin. It replaces the template placeholder with the stage workflow.

  • The plugin ran seven stages for one paper: runtime, reprod_code, reprod_report, innov_code, innov_report, self_eval, and self_evolve.
  • Five subagents ran the stages in isolated child sessions: runtime, coder, researcher, evaluator, and evolver.
  • The tools were paperloop_setup, paperloop_run, paperloop_status, paperloop_audit, and paperloop_config.
  • paperloop_setup created the app-data tree and the reproduction workspace. paperloop_run ran a stage or a slice of stages.
  • The stage time limits were 600 seconds for the first five stages and 300 seconds for the last two stages. Each limit had a plugin setting.
  • The app data held read-only configuration configs_ro/v<N>/, versioned write configuration configs_rw/v<N>/, evaluations evals/v<N>/, stage history, and run state.
  • The audit computed TCR, HIB, DCC, report compile rate, media validity, and output parity. It wrote evals/v<N>/scores.json and scores.md.
  • The plugin included a settings page, a packaged default app data seed, a TypeDoc site, the subagent contract page, and a smoke test.
