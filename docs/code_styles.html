Code style

This page renders the reference file that all PaperLoop subagents follow. The Markdown source is in .refs/code-styles.md.

Code Styles

Readability is the first priority.

General Rules

  • Use ASD-STE100 non-strict mode with academic US English fallback.
  • Use meaningful full words for every name. No exceptions.
  • Do not use an abbreviation.
  • Write a documentation string for every function, type, module, and constant. No exceptions.
  • In documentation, put one complete sentence on one or more complete lines. This rule applies to README.md and every other document.
  • Use a maximum line length of 119 characters.
  • Use line breaks to improve readability and to satisfy the line length limit.
  • Write human-understandable, minimal, necessary tests.
  • Reproduction baseline:
    • Put all input data in the read-only inputs/ directory.
    • Put all output data in the read-write and temporary .outputs/ directory.
    • Record the tool versions and the random seed for a reported result.
  • Use UTF-8 and LF.
  • End every file with a newline.

Python

  • Use the Google Python Style Guide.
  • Use 4-space indentation.
  • Use snake_case for a function and a variable.
  • Use type hints on public functions.
  • Use a Google-style docstring.
  • Use ruff for formatting and imports.
  • Use pytest with pytest.approx for a numeric test.

C and C++

  • Use the Google C++ Style Guide for C++.
  • Use the SEI CERT C Coding Standard for C.
  • Use 2-space indentation.
  • Use C17 for C and C++20 for C++.
  • Use snake_case for a function and a variable.
  • Use CamelCase for a type.
  • Compile with warnings as errors.
  • Do not invoke undefined behavior.
  • Use fixed-width integer types.
  • Use a Doxygen comment for every function, type, and constant.

C

  • Use typedef struct for a public struct type.
  • Pair malloc() with free().
  • Use snprintf() instead of sprintf().
  • Use size_t for a size.
  • Use Unity or CMocka for a test.

C++

  • Use RAII.
  • Use std::unique_ptr, std::vector, and std::string.
  • Do not use a raw new or delete.
  • Use enum class.
  • Use GoogleTest, Catch2, or doctest for a test.

R

  • Use the tidyverse style guide.
  • Use 2-space indentation.
  • Use snake_case for a function and a variable.
  • Use <- for assignment.
  • Use TRUE and FALSE.
  • Vectorize when a clear vector form exists.
  • Use a roxygen2 comment.
  • Use testthat.
  • Call set.seed() before a random number.

MATLAB

  • Use MATLAB Style Guidelines 2.0.
  • Use 4-space indentation.
  • Use lowerCamelCase for a function and a variable.
  • Use UpperCamelCase for a class.
  • Use an arguments block for every public function.
  • Preallocate an array before a loop.
  • Use a help header.
  • Use matlab.unittest.
  • Call rng(seed, "twister") before a random number.

Fortran

  • Use the Fortran-lang best practices.
  • Use 2-space indentation.
  • Use snake_case for a name.
  • Use implicit none in every program unit.
  • Use intent on every dummy argument.
  • Use allocatable instead of pointer.
  • Use error stop for a fatal error.
  • Use a Doxygen or FORD comment.
  • Use test-drive with fpm.

TypeScript

  • Use the Google TypeScript Style Guide.
  • Use 2-space indentation.
  • Use camelCase for a function and a variable.
  • Use PascalCase for a type.
  • Use const by default.
  • Do not use any.
  • Use explicit return types on exported functions.
  • Use a JSDoc comment.
  • Use node:test.

JavaScript

  • Use the Google JavaScript Style Guide.
  • Use 2-space indentation.
  • Use camelCase for a function and a variable.
  • Use PascalCase for a class.
  • Use const by default.
  • Use === and !==.
  • Use ECMAScript modules.
  • Use a JSDoc comment.
  • Use node:test.

SQL

  • Use one SQL style for the project.
  • Use uppercase keywords.
  • Use snake_case for a table and a column.
  • Use explicit JOIN clauses.
  • Do not use SELECT * in a production query.
  • Use parameterized queries.
  • Use a comment for every table, view, and function.
  • Test a query against a temporary database.

Fallback

  • Use the General Rules.
  • Use the nearest language section for a related language.
  • Use the CLRS pseudocode conventions for pseudocode.
  • State the input, output, index base, and complexity.
  • Use <- for assignment and = for equality.
  • Use require and ensure for a contract.
