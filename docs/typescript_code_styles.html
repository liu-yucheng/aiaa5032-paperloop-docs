TypeScript code style

This page renders the reference file that all PaperLoop subagents follow. The Markdown source is in .refs/typescript-code-styles.md.

TypeScript Code Styles

  • Use the Google TypeScript Style Guide as code style reference with the following exceptions.
    • Enforce a line break at the end of each complete documentation comment sentence.
    • Follow the custom line length rules.
    • Follow the custom indentation rules.
  • Use ASD-STE-100 non-strict mode with academic US English fallback as natural language style reference.
  • Use a maximum line length limit of 119 characters.
    • Use "smart" line breaks to improve sentence and code readability.
    • Do not use "dumb" line breaks that affect sentence or code readability just to satisfy the rules.
  • Use 2-space indentation.
    • Use horizontally aligned hanging indents.
    • Do not use vertically aligned indents.
  • Use complete and meaningful words to name things instead of short and confusing mathematical notations.
    • Long and clear names are better than single character names that make no sense.
    • Do not use overly abbreviated names.
  • Use const by default. Use let only when the binding changes. Do not use var.
  • Use explicit return types on exported functions and public methods.
    • Annotate a local function when inference is not obvious.
    • Do not annotate a local variable when the initializer already states the type.
  • Use unknown at an input boundary. Narrow it with a type guard before use.
    • Do not use any.
    • Do not use a non-null assertion unless a previous check proves the value.
  • Use discriminated unions for values with a closed set of shapes.
    • Handle every variant in a switch statement.
    • Use an assertNever helper in the default branch.
  • Use readonly for data that must not change after construction.
    • Use ReadonlyArray<T> or readonly T[] for arrays that the callee must not mutate.
  • Use import type for type-only imports.
    • Use named imports. Use a default import only when the module exports a default.
    • Order imports in this sequence: Node.js built-ins, external packages, internal modules, relative modules, type-only imports.
    • Use one import statement for each module.
    • Include the .js extension in a relative import when the project uses NodeNext module resolution.
  • Use async and await for asynchronous code.
    • Do not leave a floating promise. Await it or attach an explicit handler.
    • Pass an AbortSignal through every layer that can wait.
    • Use Promise.all only when the operations are independent. Use a sequential loop when one operation must finish before the next one starts.
  • Handle an error at the layer that can act on it.
    • Preserve the original error with cause when you wrap it.
    • Do not use an empty catch block.
    • Return a typed error result at a boundary that must not throw.
  • Use a small, single-purpose module.
    • A module must not import the plugin entry point.
    • A module that reads files must accept a path or a resolved layout object.
    • A module that formats text must not write files.
  • Write a documentation comment for every exported function, class, and type.
    • Enforce a line break at the end of each complete sentence.
    • Explain the contract, the important side effects, and the failure mode.
    • Do not repeat the function name as a sentence.
  • Write a comment only when the code cannot state the reason.
    • Explain why the code does something, not what the syntax does.
    • Keep a comment close to the code that it describes.
  • Use JSON.stringify(value, null, 2) + "\n" for a generated JSON file.
  • Use an atomic write for a file that another process can read: write a temporary file in the same directory, then rename it over the target.
  • Use a JSON schema with property-level required: true for a DeepSeek Harness tool parameter.
    • Do not use a top-level required array for a tool parameter schema.
    • Use additionalProperties: false on every generated object schema.
    • Use oneOf: [{ ... }, { type: "null" }] for a nullable output field.
  • Use the standard JSON Schema form for a subagent outputSchema: { "type": "object", "required": [...], "properties": { ... } }.
  • Do not use TypeScript enum or namespace.
    • Use a union of string literals and a constant object instead.
    • This keeps the source compatible with Node.js type stripping.
  • Do not use a decorator unless the framework requires it.
  • Do not use console.log in library code.
    • Use the injected logger.
    • Use console.log only in a command-line script or a self-test.
  • Use node:test and node:assert/strict for a unit test.
    • Test a pure function with a table of inputs when the cases are similar.
    • Test a file workflow in a temporary directory.
    • Do not mock the file system when a temporary directory is enough.
